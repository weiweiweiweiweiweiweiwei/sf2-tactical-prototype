## v24 完成項（2026-09-25）：操作延遲、效能、音效與使用者 UI 要求

**先量測再動手**（新工具：`tools/check.mjs --gpu intel|nvidia --size --bots --audio --nopace`，另有 `_progprobe` `_gpuab` `_audiowd` `_botmove` `_lookstats` `_lodshot` 探針）：

1. **陰影通道每幀重選著色器 46 次** → 0.1 次。three r160 對所有投影物件共用一個深度材質，蒙皮士兵和一般網格交錯時每換一次就重選一次（每次配置參數物件與字串，造成 GC 卡頓）。蒙皮網格改用專屬深度材質（`SkinnedMesh.prototype.customDepthMaterial`）。GTX 上渲染 CPU 時間 5.75 → 3.5 ms，15 秒記憶體配置 453 → 262 MB。
2. **操作延遲（內顯）**：Intel UHD 上 GPU 排隊 3–4 幀（約 100 ms 以上）。新增 `GpuPacer`（每幀插 fence）：GPU 落後時動態解析度立即下降，並在落後時最多只讓 2 幀排隊。排隊幀數降到 1–2，FPS 不變。
3. **士兵 LOD**：每個士兵 11,114 三角形，12 對 12 時一幀（含陰影）58.7 萬。15 m 外改用 1,109 三角形版本（同骨架，可逐幀切換；開鏡時依倍率算距離）。一幀降到 8.1 萬。
4. **低畫質陰影**改 1 次取樣的硬陰影（PCF 每像素 9 次取樣，Intel 上約 −1.8 ms）。
5. **結果（Intel UHD、1080p、12 對 12、倉庫）**：36 FPS、中位幀 33 ms → 60 FPS、p99 17 ms。GTX 1650 Ti：high、全解析度、60 FPS、無跳幀。
6. **音效**：舊的聲部上限會在激烈交火時把新聲音全丟掉，改成搶佔最舊的聲部。新增輸出看門狗：實測一個 NaN 樣本就讓整條輸出永久無聲（或 Chrome 重設濾波器後靜音數秒）。每 0.5 秒比對匯流排輸入與輸出，發現 NaN 或「有輸入卻無輸出」就重建整條共用匯流排，實測約 1.5 秒恢復。聆聽者朝正上／正下時保留上一個朝向（避免方向未定義）。

**使用者要求**：
- 刪除達芬奇調色系統（F8 面板、示波器、.cube LUT、Resolve 單位的色輪）。改成 SF2（Unreal Engine 3）式的固定收尾：黑點 / 亮部增益 / 中間調 / 去飽和，加對比 S 曲線，每張圖一組。各圖亮度與色度已對齊 v23（±0.002）。
- 刪除開鏡景深（Bokeh pass 與設定）。
- 刪除內顯黃色警告框（設定頁仍顯示顯卡名稱）。
- **倉庫改成獨立頁面**（開啟時隱藏房間頁）：左邊是持槍士兵 3D 展示台；右邊依序是配裝 A–E 分頁（不命名）、武器名稱與大圖、傷害 / 後座力 / 射速 / 精準度 / 彈容量、主副武器與刀和投擲物欄位、分類下拉與搜尋、3×3 分頁卡牌（滾輪或頁碼翻頁）。房間與對戰中的提示都改成 A–E（F1–F5 仍可預約）。
- **Bot 移動**：Bot 的加速與煞車改為玩家的 60%（有慣性）。開火橫移改成 0.8–1.8 秒一段，只有一半機率反向，約 25% 會站定射擊。受擊閃避從 6 m/s、0.3 秒的「瞬移」改成 3.9 m/s、0.4–0.65 秒的側步。實測交戰中的左右反向次數，倉庫從每分鐘 43 次降到 21 次，港口從 28.5 次降到 15 次；加速度 p99 從 61 降到 35 m/s²，擊殺數與 v23 相當。
- **倉庫地圖昏暗（使用者回報）**：原因是 v24 草稿的中、低畫質關掉了地圖燈光，加上低畫質的 CSS 對比以 0.5 為軸心，把暗室壓得更暗；低畫質亮度只有高畫質的約 1/3。修正後地圖燈光在所有畫質都保留（Intel 上 +1.7 ms），低畫質不再套用 CSS 對比。倉庫亮度：high 0.239、medium 0.238、low 約 0.21；其他圖低畫質也都在高畫質的 ±10% 內。

## v25 完成項（2026-10-03）：連線地基

單機玩起來不變（`tools/_feel.mjs` 腳本化輸入回歸：M4 連發 17 發、手槍點放 6 發、換彈 2.2 s、走 5.535 m、衝刺 7.241 m、跳 1.196 m 與 v24 完全相同；7 張圖 `check.mjs` 全過；Bot 90 秒擊殺數與 v24 相同）。

1. **UserCmd**（`src/12b_cmd.js`）：每個固定步長（1/120 s）把輸入打包成一個指令：移動軸、視角、後座力瞄準偏移、按住的鍵、單次按鍵邊緣（跳、換彈、擒拿、互動、Q）、切槍、開鏡等級。按鍵事件只負責「記下來」，不會漏掉短於一個步長的點擊。
2. **Human / Player 拆分**（`src/12_player.js`）：移動、衝刺、滑鏟、攀爬、梯子都改吃指令，本機玩家和遠端玩家跑同一份程式。
3. **Arsenal / WeaponSystem 拆分**（`src/11_weaponsystem.js`、`src/10_weapons.js`）：Arsenal 是武器規則（庫存、切槍、開鏡狀態、扳機、射速、換彈、刀、手榴彈、擒拿），每個步長吃一個指令；WeaponSystem 只多了第一人稱槍模和鏡頭。開火從滑鼠事件移進固定步長；瞄準改用持有者的視角，不讀鏡頭；武器計時改用 Arsenal 自己的步長時鐘。
4. **種子亂數**：每一發的散布由（玩家網路 ID、第幾發）決定（`shotRng`）。
5. **NetPlayer / Ghost**（`src/13b_netplayers.js`）：NetPlayer 是朋友在房主世界裡的士兵，指令依序號排隊、嚴格照順序重播，缺號最多等 4 個步長；Ghost 是客戶端看到的其他人，用 100 ms 延遲的快照插值。Bot 的身體動畫抽成共用的 `animateSoldier`。
6. **傳輸與工作階段**（`src/18_net.js`）：
   - `LoopbackTransport`：同一個瀏覽器的分頁用 BroadcastChannel 互通（`file://` 雙擊開啟也可以），可加人工延遲、抖動、掉包。
   - 二進位封包：指令 22 bytes／筆，每 2 步長送一包、帶最近 4 筆（掉一包不影響）；快照 30 Hz，每個角色 22 bytes，加上這段時間的子彈（27 bytes／發）。
   - `NetHost`：加入、真人取代同隊 Bot、30 Hz 快照、擊殺 / 命中 / 受傷 / 閃光事件、10 秒無訊號踢出。
   - `NetClient`：沒有 Bot、不判定傷害；自己的位置在本機預測，收到快照後比對同一個指令序號的位置，誤差小就慢慢拉回、大於 2 m 才瞬移。
   - 入口：`index.html?host=房間名`（開房，從大廳正常開始團隊死鬥）、`index.html?join=房間名`（直接加入），可加 `&lag=80&jitter=20&loss=0.05&name=暱稱&team=bravo`。
7. **驗證**（`tools/_nettest.mjs`：兩個分頁，一個開房一個加入）：

   | 條件（每個方向） | 移動後位置誤差 | 子彈方向（客戶端預測 vs 房主） | 其他 |
   |---|---|---|---|
   | 40 ms、抖動 10 ms、掉包 2% | 2.3 cm | 前 5 發的指令序號、瞄準、散布完全相同 | 擊殺、受傷、死亡、5 秒後重生都同步 |
   | 150 ms、抖動 30 ms、掉包 10% | 2.8 cm | 同上 | 同上 |

**和原計畫不同的地方**：計畫寫「AI、規則也全部移進固定步長」，但房主制是房主說了算、客戶端不重算 AI，所以只有「客戶端要預測」的部分（自己的移動和武器）需要逐步長一致。AI 和規則維持原樣，降低風險。

**v25 的限制（之後版本處理）**：只支援團隊死鬥；手榴彈、掉槍、拾取不同步（客戶端只看得到自己丟的手榴彈）；還沒有延遲補償（打移動中的目標要提前量）；房主分頁切到背景時整場會停住，測試時兩個視窗都要在螢幕上。

## v26 完成項（2026-10-03）：跨電腦連線

- **Supabase 專案** `sf2-tactical`（東京 ap-northeast-1，免費方案，$0）：只用 Realtime，不建任何資料表。
  - `sf2:lobby` 頻道：用 Presence 公告開放中的房間（代碼、房主暱稱、地圖、賽制、人數）。房主離線時，房間自動從列表消失。
  - `sf2:room:代碼` 頻道：傳 WebRTC 交握訊息（offer / answer / ICE）。
  - 網頁裡用的是 publishable key，本來就是設計給前端公開的。
- **WebRTC 傳輸**（`src/18b_online.js`）：每位朋友兩條 DataChannel，`r` 是可靠且有序（事件），`u` 是不可靠且無序（指令、快照）。`RtcHostTransport`、`RtcClientTransport` 的介面和 `LoopbackTransport` 相同，所以 NetHost 和 NetClient 不用改。STUN 用 Google 和 Cloudflare，最多 8 人。
- **大廳**：
  - 新增「線上對戰」區塊：暱稱、「出發時開放線上房間」（只限團隊死鬥）、輸入代碼加入、房間列表（即時更新，可直接加入）。
  - 大廳設計高度 820 → 860，地圖縮圖改成一排 7 張。修正 v24 就有的問題：1440×860 畫面下「出發」按鈕被切掉一半。

## v32 完成項（2026-10-04）：TURN 中繼（Metered）

- **為什麼需要**：手機熱點、公司或學校網路常會擋掉點對點直連。TURN 伺服器幫兩邊轉送資料，連不上直連的人也能玩。
- **方案**：使用者選 **Metered**（免綁卡，每月 500 MB；Cloudflare 每月 1,000 GB 但要綁卡）。實際上只有連不上直連的人才會用到中繼，對戰流量每人每小時約 30–50 MB。
- **Edge Function `turn`**（`supabase/functions/turn/index.ts`，verify_jwt 關閉）：
  - 金鑰存在 Supabase Secrets（`METERED_APP`、`METERED_API_KEY`），不會出現在網頁裡。函式向 Metered 取得 ICE servers 給遊戲，只接受遊戲網址的請求，同一個執行個體 30 分鐘內重用結果。
  - 也支援 Cloudflare（`CF_TURN_KEY_ID`、`CF_TURN_TOKEN`），以後要換只需改 Secrets。
  - 除錯紀錄：第一次填了錯的 Key（Metered 回 401），換成憑證網址裡 `apiKey=` 後面的值才成功。
- **遊戲端**：開房和加入時一起取得中繼設定（3.5 秒逾時就退回只用 STUN）。連線會優先直連，直連不通才走中繼。暫停選單顯示「直連／經中繼伺服器」（房主看到「N 人經中繼伺服器」），FPS 列加上「中繼」。網址加 `?relay=1` 會強制只走中繼，用來測試。
- **驗證**：
  - `node tools/_samebrowser.mjs relay`：強制只走中繼，約 6.5 秒進房，一起開打。朋友端顯示 relay，房主顯示 1 人經中繼。不強制時照常 direct。
  - `RELAY=1 node tools/_nettest.mjs rtc`：全程走中繼，移動後位置差 2.4 cm，命中、擊殺、重生同步。
- **另外查了「卡頓、GPU 很吃」**（`tools/_perfver.mjs`、`_gpuuse.mjs`、`_cpuprof.mjs`、`_pacetest.mjs`、`_gpuab2.mjs`）：
  - 現在的版本和 v24 在 Intel UHD 1080p 上都是約 33 FPS，GPU 用量相同，選單都是 0%。
  - NVIDIA GTX 1650 Ti 上是 60 FPS、高畫質。
  - 結論：遊戲沒有變慢，是 Chrome 改用了 Intel 內顯。已請使用者在 Windows 圖形設定把 Chrome 設成高效能。
  - 內顯上關陰影、降解析度、關 HUD、拿掉 CSS 濾鏡都只差 1–4 FPS。GPU 跳幀機制少 4 FPS，但能避免多 50–100 ms 的延遲，所以保留。
